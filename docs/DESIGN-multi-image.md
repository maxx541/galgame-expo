## 為什麼想做這個

週邊跟一般圖片不一樣，**很多資訊在正面以外**：

- 立牌：背面的印刷、底座的形狀、包裝袋
- 掛畫：布料質感、邊緣車線、附的收納筒
- 原畫集：封面、書背、內頁跨頁、附錄別冊
- 限定特典：本體 + 外盒 + 說明卡，三件才是完整的一套

目前一件展品只能放一張圖，等於逼你在「拍正面」跟「拍細節」之間二選一，
或是把同一件東西拆成好幾筆展品（那樣分類統計會失真，逛起來也很怪）。

**但這不是非做不可。** 如果你的收藏大多是平面類（色紙、掛畫），
一張正面照其實就夠了，那這個功能對你的價值就不高。
**先看你手上的東西再決定。**

---

## 三個方案

### 方案 A：不做，用「備註」補足

在備註欄寫「背面印刷為燙金、附原包裝」之類的文字描述。

- **成本**：0
- **適合**：平面類收藏為主、或你不打算拍那麼多張
- **缺點**：文字終究不如圖

先老實說：**如果你不確定，這就是正確答案。**
等你真的拍了一堆細節照卻沒地方放，再回來做 B 或 C。

---

### 方案 B：加一個 `images` 陣列欄位（推薦）

資料表加一個 `jsonb` 欄位存額外的圖，原本的 `image_url` 保持不動當封面。

```sql
alter table public.exhibits
  add column if not exists images jsonb not null default '[]'::jsonb;
-- 形狀：[{ "url": "...", "public_id": "...", "w": 1200, "h": 1600, "caption": "背面" }]
```

**為什麼是新增欄位而不是改成關聯資料表？**

一件展品的圖片數量頂多 5–10 張，而且**永遠只會跟這件展品一起讀取**，
不需要單獨查詢、不需要跨展品做統計。這種情況下開一張 `exhibit_images` 表
只會讓每次讀取都多一次 join，換不到任何好處。`jsonb` 是更合適的形狀。

**為什麼保留 `image_url` 當封面，而不是把第一張當封面？**

1. 現有的 100 多筆資料完全不用搬，加了欄位就能直接跑（舊資料的 `images` 是空陣列）
2. 封面是「要出現在牆上的那張」，跟「第幾張」是兩件事 ——
   你可能想把背面照排在第二張，但封面用的是修過圖的正面
3. `list()` 查詢可以完全不動

**要改的東西：**

| 檔案 | 改什麼 | 份量 |
|---|---|---|
| `supabase/schema.sql` | 加一個 `images jsonb` 欄位 | 1 行 |
| `store.js` | `normalizeItem` / `toRow` 帶上 `images` | ~10 行 |
| `lightbox.js` | 燈箱內加一排「這件展品的其他角度」縮圖，可切換 | ~60 行 |
| `admin.js` | 上傳時可指定「這批是同一件的多角度」；編輯時可增刪圖 | ~120 行 |
| `styles.css` | 那排縮圖的樣式 | ~40 行 |

**估計：3–4 小時**，其中後台的編輯介面最花時間。

**一個要先想清楚的互動問題：**
燈箱底部現在已經有一排膠卷縮圖了（那是「整個展覽的其他展品」）。
再加一排「這件展品的其他角度」會有兩排縮圖，很容易混淆。

我的建議：**把展品內的多角度切換做在圖片本身上** ——
圖片左右各一個小箭頭 + 右上角顯示「2 / 4」，
跟「切換到下一件展品」的大箭頭在視覺上明確分開。
手機上則是：左右滑 = 換展品（維持現狀），上下滑 = 換角度。

> 這個互動我沒把握一次就對，建議實作時先做桌機版，你試用過再決定手機的手勢。

---

### 方案 C：拆成獨立的 `exhibit_images` 資料表

正規化做法，一張表存所有圖片，用 `exhibit_id` 關聯。

- **好處**：可以單獨查詢圖片、可以排序、可以對單張圖加標籤
- **壞處**：每次讀取都要 join 或第二次查詢；RLS 政策要寫兩套；
  後台的狀態管理複雜不少

**對這個規模來說是過度設計。** 除非你之後想做「所有展品的背面照集錦」
這種跨展品的圖片查詢，否則 B 就夠了。

## 我的建議

**先不要做。**

理由：你現在連一張真實照片都還沒上傳。
「一件展品需要幾張圖」這件事，要看過你實際拍出來的東西才知道 ——

- 如果你拍下來發現大多數東西一張正面照就夠了 → 方案 A，省下 4 小時
- 如果你發現一直想補背面 → 方案 B，而且那時你已經知道**通常需要幾張**、
  **想怎麼標註**（「背面」「外盒」「附錄」），設計會準確得多

現在就動手的話，我是在猜你的需求。等你傳完第一批照片，答案會自己浮出來。

**如果你就是想先做**，選方案 B，我可以在下一輪排程完成。
資料庫改動是「只新增欄位、不動既有資料」，完全可逆，風險很低。
